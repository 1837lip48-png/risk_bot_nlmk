## Контекст

Строим **RiskLesson** — приложение управления рисками проекта с формированием уроков (lessons learned). Это не проект с нуля: два готовых HTML-прототипа уже задают логику, роли и часть визуального языка:

- **`docs/prototypes/RiskLesson - Вход.html`** — вход по имени/фамилии → выбор одной из 3 ролей → модалка СПП → переход в `workspace.html`. Полностью рабочий, включая AI-подсказку «Возможный дубль» в форме подачи риска для роли Инициатор.
- **`docs/prototypes/workspace.html`** — рабочее пространство с 7 вкладками, уже наполненное **настоящими данными**: 15 реальных рисков проекта ЦГП-2 (из `ЦГП-2_ТОП-Риски_апр_26.pdf`) и 10 реальных уроков проекта БВН (из `Reestr_urokov_BVN_shablon.xlsx`), с рабочим аккордеоном мероприятий, светофором и матрицей 3×3.

Оба файла — на самодельных CSS-переменных (токены «в духе» `@nlmk/ds-2.0`, не сам пакет) и чистом JS. Это референс **логики, раскладки экранов и реальных данных**, а не код для копирования 1:1 в продакшен.

Полное описание бизнес-процесса — `docs/process_full_v4.md`. Каталог реальных UI-компонентов — `docs/nlmk_ds2_components.md`. Сведённая дизайн-система из Figma-референсов (второстепенно, только для смысловых параллелей, стек Tailwind/shadcn оттуда **не используется** — см. «Ограничения») — `docs/design_system.md`.

Этот репозиторий ранее уже содержал отдельный прототип «RiskAssess Bot» (`streamlit_app/`, `lessons_learned_interface.html`) — более ранняя, не идентичная итерация той же задачи. Он не трогается и не используется как источник логики для RiskLesson; оставлен как есть, как история.

## Цель

Пересобрать логику и данные из прототипов в настоящее React-приложение с реальной моделью данных, персистентным слоем и всеми бизнес-правилами из `process_full_v4.md` — не переписывая процесс заново, а реализуя уже принятые решения.

## Стек

- **Frontend: React + TypeScript + `@nlmk/ds-2.0`** — решено, не открытый вопрос. Реальный корпоративный npm-пакет (`nlmk-group/ds-2.0`, `https://nlmk-group.github.io/ds-2.0`). Прочитай `docs/nlmk_ds2_components.md` перед вёрсткой любого экрана — там таблица «компонент → где именно использовать». Свой CSS — только там, где в пакете нет аналога: Карта взаимосвязей (SVG-холст), Матрица рисков (сетка 3×3), Knowledge Graph.
- **Backend / API: Python + FastAPI** — решено. Причина выбора (обсуждалось перед стартом): AI-функции (AI-подсказки по дублям, генерация черновика урока, Executive Summary, Knowledge Graph) удобнее строить в Python-экосистеме, чем оборачивать вызовы LLM поверх Node. Структура: `backend/app/` (models / schemas / api / services), Pydantic для DTO, `python-jose` не нужен — авторизации по паролю нет.
- **База данных: PostgreSQL + SQLAlchemy 2.0 (ORM) + Alembic (миграции)** — решено. Реляционная модель из раздела 5 (`Risk`/`Action`/`Lesson`/`RiskDependency`/`AuditLog`) с массивами (`ownerIds` → `ARRAY(Integer)`) и JSON-полями (`scenarios`, `pChecklist`) ложится на Postgres напрямую. Разворачивается вместе с backend в одном Docker Compose — соответствует масштабу «внутренний инструмент на 10–50 пользователей», не требует managed-облака.
- Аутентификация: без пароля, по имени/фамилии + выбор роли — осознанное решение процесса, не строить полноценный auth-провайдер, но нужна таблица пользователей.
- **AI-функции (AI-подсказки, генерация уроков, Executive Summary, Knowledge Graph): Anthropic API (Claude)** — решено, вызывается напрямую из FastAPI-сервисов (`backend/app/services/ai/`).

## Модель данных

Полная схема — `process_full_v4.md`, раздел 5. Ключевое, что нельзя упростить при реализации:

- **`Risk.id`** — составной код (`12-1111-1-1Ri`), глобально уникальный, это первичный ключ. **`Risk.displayNumber`** — простой номер (`90`, `92`...) только для печатных паспортов/отчётов, не обязан быть уникальным глобально. Оба поля нужны, это не взаимоисключающий выбор.
- **`Risk.ownerIds`** — массив, не одно значение (реальные экономические риски показывают до 3 совладельцев).
- **`Action.strategy`** и **`Action.kind`** — поля мероприятия, а не риска. `strategy`: Снижение / Передача / Уклонение / Принятие. `kind`: Причина / Следствие / Запасной план / Существующая процедура. У «Запасной план» есть текстовый `triggerCondition`.
- **`Action.plannedDate`** и **`Action.forecastActualDate`** — два разных поля, не одно.
- Статус-конвейер риска: `Идентификация → Анализ и оценка → Управление → Мониторинг и Контроль → Закрыт` (решено — стадия «Закрыт» нужна как триггер формирования урока, даже если в изученных реальных данных она пока не встретилась). Отдельная ветка `Архивирован (объединён с [ID])` — только для дублей.
- `RiskDependency.source` (`manual` | `ai_suggested`) обязателен — разделяет ручную Карту связей и AI Knowledge Graph.
- Каждый переход статуса риска пишется в `AuditLog`.

## Методология оценки (не придумывать заново — она уже есть, реальная)

- **P** — чек-лист из 3 вопросов Да/Нет → детерминированно даёт 1/2/3.
- **I** — описательная шкала 1–3, I=3 обязательно с текстовым обоснованием.
- **RRA = P×I**, матрица 3×3: 1–2=L, 3–4=M, 6–9=H. Зон **три**, не четыре — отдельной «Critical» нет.
- **Эскалация комитету** триггерится при **I=3** (не зоной RRA) — отдельный флаг на карточке, не 4-й цвет severity.
- **EL = Вероятность(%) × Влияние на бюджет (млн ₽)**, суммируется по портфелю.
- **Светофор риска** (агрегат статусов мероприятий): 🟢 всё выполнено · 🔵 идёт по плану · 🔴 просрочено или мероприятий нет · ⚫ всё отклонено · 🟡 всё ещё «Планируется».

## Экраны (порядок реализации)

1. **Вход** — уже реализован в прототипе, переносить логику как есть.
2. **Форма подачи риска** (Инициатор) — AI-подсказки по паузе в наборе И по blur, тексты кнопок дословно: «Открыть существующий» / «Всё же создать новый» / «Посмотреть урок».
3. **Дэшборд** — разный набор виджетов для риск-менеджера и владельца риска (см. ниже, экран 3.1).
   - **3.1 Персональный экран владельца риска** (не то же самое, что персонализированный Дэшборд менеджера) — «Мои риски» + «Что от меня требуется» (Согласовать/Выполнить/Отклонить с комментарием). Фильтр по владельцу в реестрах для этой роли — задизейблен, не просто предустановлен.
4. **Реестр рисков** — карточки с аккордеоном мероприятий (`Accordion` из `@nlmk/ds-2.0`), фильтры (`Filter`/`FilterTip`), статус-машина.
5. **Карта взаимосвязей** — двойная точка входа: и переключатель «Список/Карта связей» внутри Реестра рисков, и отдельный пункт сайдбара — оба ведут на одно состояние. Тип связи — фиксированный список (не свободный текст). Объединение дублей — модалка с постатейным выбором значений по каждому расходящемуся полю.
6. **Матрица рисков** — сетка P(1–3)×I(1–3), не 5×5.
7. **Реестр уроков** — реальные 14 полей (см. `process_full_v4.md` разд. 4.6), хештеги как есть в прототипе, кнопка «Создать риск на основе урока».
8. **Календарь** — три типа событий (мероприятие / пересмотр / согласование).
9. **Privacy Reports & Analytics** — Executive Summary + Knowledge Graph на одной вкладке, последней по очереди (зависит от данных остальных экранов).

## Обязательное использование `@nlmk/ds-2.0`

Не изобретай свои аналоги там, где компонент уже есть — см. полную таблицу в `nlmk_ds2_components.md`. ## Seed-данные — использовать реальные, не выдумывать новые

В `workspace.html` уже перенесены **15 реальных рисков** (ЦГП-2) и **10 реальных уроков** (БВН) с полными описаниями, мероприятиями и хештегами. Возьми их как seed для БД — это сразу проверяет, что аккордеон, светофор, фильтры и матрица работают на реальных данных, а не на удобных моках.

- Не подключай Tailwind/shadcn — фронтенд строится на `@nlmk/ds-2.0`.

# RiskLesson — полное описание процесса (v4, для разработки)

> v4: методология оценки (P/I/RRA/EL), поля мероприятий, светофор, реестр уроков и формат Risk ID заменены реальными данными НЛМК (методология + рабочий Excel-реестр + PDF «ТОП-риски») вместо решений по умолчанию из v3. Расхождения между реальными источниками помечены явно, а не тихо разрешены в одну сторону.

---

## 1. Роли и доступ

| Роль | Выбирается на входе | Права |
|---|---|---|
| **Риск-менеджер** | Да | Полный доступ ко всем рискам/урокам проекта, верификация оценок, переводы статусов, эскалация, полный доступ к Карте связей, управление проектами |
| **Владелец риска** | Да | Управление только своими рисками: стратегия, мероприятия, остаточная оценка, проверка черновика урока; связи/объединение — только в рамках своих рисков |
| **Инициатор** | Да | Только подача риска через компактную форму; не входит в общее пространство |
| **Ответственный за мероприятие** | Нет, назначается внутри карточки | Обновление статуса/срока своего мероприятия |
| **Риск-комитет** | Нет — не пользователь приложения | Получает эскалации, решения фиксируются риск-менеджером от их имени |
| **[РЕШЕНИЕ] Администратор** | Отдельная системная роль, не в списке входа | Создаёт проекты и СПП-коды, управляет справочниками (категории, шаблоны отчётов) |

## 2. Проекты и вход в систему

- Вход без пароля: **Имя + Фамилия** → выбор роли → код **СПП** (формат `NN-NNNN`) существующего проекта → «Войти в систему».
- **[РЕШЕНИЕ — пробел 1]** Проект создаётся отдельно, до того как кто-либо сможет по нему войти:
  - Экран **«Проекты» (доступен только Администратору)**: список проектов, кнопка «Создать проект» → форма (Название проекта, СПП-код — генерируется автоматически по маске `ГГ-XXXX`, куратор, дата старта).
  - При создании проекта Администратор назначает первого риск-менеджера — дальше риск-менеджер сам добавляет владельцев рисков и инициаторов в проект (через экран «Участники проекта», справочно).
- Если у пользователя одна роль в системе — экран выбора роли можно пропустить (не блокирующее правило, применяется когда пользователь уже известен системе по имени/фамилии).

## 3. Полный жизненный цикл риска

```
Идентификация → Анализ и оценка → Управление → Мониторинг и Контроль → Закрыт
                                                                          ↓
                                                                 Реестр уроков (Lesson)
```
Отдельная ветка вне основного конвейера: **Архивирован (объединён с [ID])** — только для дублей.

### Этап 1. Подача / идентификация риска
- Инициатор — через компактную модальную форму (Категория, Наименование, Риск-событие, Прямое следствие, Предполагаемый владелец).
- Риск-менеджер/владелец — тем же набором полей прямо в карточке риска.
- AI-подсказки при вводе риск-события: «Возможный дубль» (поиск похожих формулировок в реестре) и «Похожий урок в базе» (обратный поиск по Реестру уроков).
- Риск создаётся сразу со статусом **«Идентификация»**.

### Этап 2. Качественная и количественная оценка
**[ЗАМЕНЕНО реальной методологией НЛМК из «Методология и поля реестра рисков» — предыдущая версия этого раздела была моей выдумкой и не соответствовала действительности]**

Оценка строится в **два параллельных, независимых слоя** — качественный (детерминированный, по чек-листам) и количественный (прямое экспертное суждение). Один слой не подменяет другой, оба хранятся и прослеживаются раздельно.

**Качественная оценка вероятности (P), шкала 1–3:**
Владелец риска отвечает на 3 вопроса Да/Нет:
1. Есть ли точные данные о причине риска?
2. Достаточно ли стандартных процедур для предотвращения риска?
3. Требуются ли внешние компетенции для управления риском?

Балл начисляется за признаки неопределённости (ответ «Нет» на 1–2, «Да» на 3). Сумма баллов (0–3) детерминированно даёт **P = 1, 2 или 3** — свободный ввод числа не допускается.

**Качественная оценка материальности (I), шкала 1–3, описательная:**
- I = 1 (низкое) — не влияет существенно на результаты проекта
- I = 2 (среднее) — требует контроля и корректирующих действий, цели остаются достижимыми
- I = 3 (высокое) — существенно влияет на результаты проекта, **требует эскалации на управляющий комитет** (это и есть источник правила «эскалация при I=3» из этапа 3)

Выбор I обязательно сопровождается текстовым обоснованием.

**RRA (качественный, автоматический) = P × I, матрица 3×3:**
| P×I | Зона |
|---|---|
| 1–2 | **L** (низкий) |
| 3–4 | **M** (средний) |
| 6–9 | **H** (высокий) |

Зон всего **три**, не четыре — отдельной зоны «Critical» в методике нет. Полученное значение определяет приоритет в реестре и необходимость эскалации.

**Количественная оценка — отдельным блоком, без формул методики:**
Эксперт (владелец риска, при необходимости с экономистом) даёт: вероятность реализации в %, влияние на срок (мес.), влияние на бюджет (млн ₽). При необходимости — три сценарные точки (оптимистичная / наиболее вероятная / пессимистичная).

**EL (Expected Loss) = Вероятность (%) × Влияние на бюджет (млн ₽).** Суммируется по всем открытым рискам → «Совокупный ожидаемый ущерб» на дэшборде.

**Сверка слоёв:** если качественный уровень L, а количественная EL аномально высока — сигнал перепроверить одну из оценок вручную. Автокоррекции одного значения на основании другого нет.

**Основания оценки (обязательны):** для P — ответы чек-листа; для I — текстовое обоснование уровня; для количественной — комментарий эксперта («на основании чего именно такие проценты и суммы»); для обеих — автор и дата.

Верифицирует обе оценки риск-менеджер: корректность чек-листа P, обоснованность I, правдоподобие количественных цифр относительно похожих рисков в портфеле. Расхождения фиксируются в журнале с текстовым основанием.

Статус: `Идентификация` → `Анализ и оценка`.

### Этап 3. Эскалация (при необходимости)
**[РЕШЕНИЕ — пробел 6, ИСПРАВЛЕНО после повторного чтения «Жизненный цикл v2»] Механизм эскалации риск-комитету:**
- Триггеры — дословно по документу: **I = 3** (не I = 5, как было ошибочно решено в первой версии этого файла) **или** существенное расхождение качественной и количественной оценки.
- Риск автоматически помечается флагом **«Требует решения комитета»** (визуальный бейдж на карточке и в реестре).
- Риск-менеджер видит такие риски в отдельном виджете дэшборда «На эскалации» и вручную формирует выгрузку/письмо комитету (кнопка «Подготовить материал для комитета» — генерирует краткую сводку по риску).
- Решение комитета риск-менеджер вносит вручную в карточку риска (поле «Решение комитета» + дата), это пишется в Audit Log. Комитет не имеет своего логина.

### Этап 4. Назначение владельца, стратегия, мероприятия
**[ИСПРАВЛЕНО по реальным паспортам рисков НЛМК]** Стратегия управления риском — фиксированный список из 4 значений (реальные подписи, не мои переводы PMI-терминов):
- **Снижение** — мероприятия, уменьшающие P и/или I
- **Передача** — страхование, аутсорс, договорная передача ответственности
- **Уклонение** — исключение причины риска (смена подхода/решения)
- **Принятие** — осознанно ничего не делать, с обоснованием

**Важная поправка:** в реальных данных стратегия указывается **на уровне каждого мероприятия, а не одна на весь риск** — у одного риска мероприятия могут иметь разные стратегии одновременно (например, часть — «Снижение», одно — «Передача», ещё одно — «Уклонение»). Поле `strategy` в модели данных переносится с `Risk` на `Action`.

**Вид мероприятия** — фиксированный список из 4 значений (не бинарный Причина/Следствие, как было решено раньше):
- **Причина** — превентивная мера, снижает вероятность (P)
- **Следствие** — мера реагирования на уже наступившее событие, снижает влияние (I)
- **Запасной план** — контрметра на случай срабатывания основной; всегда сопровождается текстовым **триггером** («Триггер: <условие>»), встроенным прямо в описание мероприятия, а не отдельным полем
- **Существующая процедура** — мероприятие ссылается на уже действующий процесс/регламент, а не на новое действие

Владелец риска создаёт мероприятия (задача, вид, исполнитель, срок, стоимость). Статус риска: `Анализ и оценка` → `Управление`.

**Владелец риска — может быть больше одного человека.** Реальные карточки экономических рисков показывают нескольких совладельцев (например, «Аршакуни К.В., Гущин И.В., Хорн С.О.» на одном риске) — поле `ownerId` в модели данных должно быть массивом, не одиночным значением.

### Этап 5. Исполнение мероприятий
**[ДОПОЛНЕНО реальной методологией — раньше этой логики не было]**

Карточка риска — верхний уровень записи, всегда видна в списке. Мероприятия — нижний уровень, скрытый по умолчанию, раскрывается по наведению/клику на строку риска (аккордеон). Это не две таблицы, а иерархия «один риск → много мероприятий».

**У каждого мероприятия — два разных поля срока**, специально раздельных:
- **Плановый срок реализации** — фиксируется один раз при утверждении, не меняется
- **Прогноз/факт срок** — обновляется по ходу исполнения (сначала прогноз, по завершении — факт)

Разница между ними — индикатор просрочки.

**Статус мероприятия** — собственный цикл, отдельный от статуса риска: `Планируется → В работе → Выполнено`, либо `Отклонено`.

**Светофор риска — агрегация статусов мероприятий в цветовой индикатор**, видимый в строке риска без разворачивания аккордеона:
| Цвет | Условие |
|---|---|
| 🟢 Зелёный | Все мероприятия выполнены |
| 🔵 Синий | Работа идёт, план vs факт/прогноз не нарушены |
| 🔴 Красный | Хотя бы одно мероприятие просрочено, или мероприятий нет вообще |
| ⚫ Серый | Все мероприятия отклонены |
| 🟡 Жёлтый | Все мероприятия ещё «Планируется» |

Ответственный за исполнение мероприятия обновляет его статус — статус риска при этом переходит `Управление` → `Мониторинг и Контроль`, как только хотя бы одно мероприятие переведено в «В работе».

Сроки мероприятий и дата следующего пересмотра риска — источник событий для Календаря.

### Этап 6. Мониторинг, картирование связей
- Статус: `Управление` → `Мониторинг и Контроль`.
- **Карта взаимосвязей** (внутри Реестра рисков, режим просмотра): ручное построение связей между рисками.
  - Режимы: Курсор / Риск / Связать / Объединить.
  - Связь = отдельная сущность `risk_dependency` (риск-источник, риск-цель, тип связи из списка: *усиливает, ведёт к, зависит от, дублирует*, автор, дата).
  - Объединение дублей — риск, признанный дублем, архивируется с пометкой «объединён с [ID]», мероприятия переносятся к оставшемуся риску без автодедупликации.
  - Права: риск-менеджер — без ограничений; владелец — только для своих рисков; инициатор — доступа нет.

### Этап 7. Остаточная оценка
**[ДОПОЛНЕНО]** Тоже в двух независимых слоях:
- **Качественный остаточный RRA** — рассчитывается автоматически через 3 вопроса о статусе мероприятий (все ли переведены в «В работе»? все ли выполнены? реально ли выполненные меры митигируют риск?). Ответ определяет снижение уровня по той же матрице 3×3.
- **Количественный остаточный EL** — эксперт оценивает заново, с учётом уже внедрённых мер. Это новое самостоятельное суждение, **не автоматическое уменьшение исходной суммы на процент**.

### Этап 8. Закрытие риска
Риск-менеджер закрывает риск. Статус: `Мониторинг и Контроль` → `Закрыт`. Каждый переход статуса пишется в **AuditLog** (кто, когда, что, комментарий) — это и есть требуемая «прослеживаемость статуса».

### Этап 9. Формирование урока
- При закрытии риска LLM-ассистент готовит черновик урока (заголовок, описание, категория, рекомендация «Start/Continue/Stop», ссылка на исходный риск).
- Владелец риска проверяет и публикует урок в Реестре уроков.
- Урок участвует в AI-подсказке «Похожий урок» на этапе 1 нового риска.
- Из карточки урока доступна кнопка **«Создать риск на основе урока»** — открывает форму создания риска с предзаполненными полями и обратной ссылкой `source_lesson_id` (трассируемость Lesson ↔ Risk в обе стороны).

## 4. Экраны и их содержимое

### 4.1 Дэшборд
**[ИСПРАВЛЕНО реальным примером листа «Риски 2/3» из рабочего Excel]** Итоговый состав виджетов:
- KPI: Активные риски, **Высокая критичность (RRA=H)** — не «Critical», зон всего три; Просроченные мероприятия; Уроков сформировано за период
- **Риски по категориям** — счётчик + доля, ровно как в реальном листе «Риски 2»: Технологические / Технические / Процессные / Регуляторные / ПИР / СМР/ПНР / Снабжение / Экономические
- **Риски по статусу** — счётчик + доля: Идентификация / Анализ и оценка / Управление / Мониторинг и Контроль (в реальных данных статус «Закрыт» ни разу не встретился — возможно, это будущая стадия, которую стоит подтвердить отдельно, а не считать подтверждённой)
- **Мероприятия по статусу выполнения** — счётчик + доля: Выполнено / В работе / Планируется / Отклонено
- Audit Log — последние переходы статусов
- Мероприятия, требующие внимания (ближайшие/просроченные)
- Уроки на проверке (черновики от AI)
- Виджет «На эскалации» (риски с флагом «Требует решения комитета», I=3) — только у риск-менеджера
- Для владельца риска — тот же набор, отфильтрованный только по его рискам, плюс блок «Что от меня требуется» (согласовать / выполнить)

### 4.2 Календарь
**[РЕШЕНИЕ — пробел 4]** Отдельная вкладка, показывает три типа событий:
- Срок мероприятия (из карточек риска)
- Дата пересмотра риска (плановая переоценка, по умолчанию раз в 30 дней для Medium/High, раз в 14 дней для Critical)
- Просроченные события — отдельным цветом
Клик по событию открывает соответствующую карточку риска.

### 4.3 Реестр рисков
Список/карточки риска, фильтры по категории/статусу/степени серьёзности, поиск, кнопка «Добавить риск», счётчик связей на каждой карточке, переключатель в режим Карты взаимосвязей.

**[НОВОЕ] Детальный просмотр риска — «Паспорт риска».** Реальный формат НЛМК для просмотра/печати одного риска (см. приложенный `ЦГП-2_ТОП-Риски_апр_26.pdf`) — этим же макетом стоит закрыть модалку/страницу «Детали риска»:
- Заголовок «Паспорт риска. <Наименование>» + лого
- Левая колонка «Основные данные риска»: ID риска, Статус, Категория, Владелец риска
- Центр «Полное описание риска» — 3 блока с иконками: Причина / Риск-событие / Прямое следствие
- Правая колонка «Уровень критичности» — крупная надпись цветом (Высокий=красный, Средний=янтарный, Низкий=зелёный — 3 уровня, не 4)
- Таблица «РЕАГИРОВАНИЕ» на всю ширину: Стратегия управления риском / Мероприятие / Вид мероприятия / Ответственный за исполнение / Плановый срок реализации / Стоимость мероприятия / (опционально Фактический срок реализации) / Статус выполнения мероприятий
- Кнопка «Экспорт паспорта» (PDF) — раз формат уже используется НЛМК как отчёт, разумно дать возможность выгрузить в этом же виде прямо из карточки риска.

### 4.6 Реестр уроков
**[ЗАМЕНЕНО реальной структурой из «Реестр уроков БВН шаблон.xlsx» — 14 колонок, с примерами по реальному проекту]** Поля карточки урока:
- **ID урока** (`L-01`, `L-02`, ...)
- **Проект** (откуда урок — может быть другой проект, не только текущий)
- **Фаза** (на какой фазе проекта возникла ситуация)
- **Категория** — более гранулярная, чем 8 категорий рисков (например «Проектирование / компоновка», «Закупки / тендер», «СМР / материалы») — по сути «категория риска» + подкатегория через слэш
- **Наименование**
- **Проблема / Риск-событие**
- **Описание** (что произошло, подробно)
- **Корневая причина**
- **Влияние** — текстовое поле произвольного формата, реально заполняется как «547 млн ₽ / 10 мес.» (деньги + срок вместе, не отдельные структурированные числа)
- **Триггер / индикатор** (по какому признаку риск можно было распознать заранее)
- **Стратегия реагирования** (то же поле, что и у риска — Снижение/Передача/Уклонение/Принятие)
- **Выученный урок** — обобщение, генерализация проблемы
- **Рекомендация / Действие** — конкретное действие на будущее
- **Хештеги** — свободные теги через `#`, используются для фильтрации (это и есть содержимое tag-pool/tag-drop панели, которая уже реализована в `workspace.html`, но не была наполнена данными)

Поле `sourceRiskId` физически видно только внутри «Описания»/«Триггера» текстом — нет отдельного структурированного ID риска-источника в реальном шаблоне. Для трассируемости Lesson↔Risk в новой системе стоит добавить отдельное структурированное поле `sourceRiskId`, но UI подписи полей (Наименование, Категория, Влияние и т.д.) должны совпадать с реальным шаблоном дословно.

### 4.7 Privacy Reports & Analytics (AI)
**[РЕШЕНИЕ — пробел 5]** Отдельная вкладка, не путать с ручной Картой взаимосвязей:
- **Executive Summary** — авто-сгенерированная сводка: общий уровень риска и тренд, число выявленных рисков, суммарный EL портфеля, просроченные мероприятия, ключевые достижения, приоритетные действия.
- **Knowledge Graph** — AI-предлагаемые связи между рисками и уроками на основе схожести формулировок и общих причин (в отличие от ручных связей на Карте — эти помечены флагом `source: ai_suggested` в той же сущности `risk_dependency`, требуют подтверждения риск-менеджером перед тем как стать «ручными»).
- Кнопка «Просмотреть в Карте взаимосвязей» — переносит подтверждённую AI-связь в основную карту.

## 5. Модель данных (для промта в Claude Code)

**[РЕШЕНО]** Формат Risk ID разный в двух реальных документах:
- Рабочий мастер-реестр (Excel «Свод по проекту») использует составной код: `12-1111-1-1Ri` (СПП проекта + номер риска + суффикс «Ri»)
- Отчёт «ТОП-риски» (PDF-паспорта) использует простой сквозной номер: `90`, `92`, `36`...

**Решение:** составной код — это `id` записи в базе (глобально уникален, на него ссылаются мероприятия, связи, уроки). Простой номер — это `displayNumber`, генерируется отдельно для печатных паспортов/отчётов (уникален только в рамках конкретного отчёта, не в БД). Оба формата реально используются НЛМК для разных целей, поэтому оставлены оба, а не выбран один в ущерб другому.

```
User        { id, name, surname, projectRoles: [{projectId, role}] }
Project     { id, sppCode, name, curator, startDate }
Risk        { id, displayNumber, projectId, title, category, status,
              authorId, ownerIds: [userId],           // массив — риск может иметь нескольких владельцев
              identificationDate, identificationPhase, // фаза, на которой риск обнаружен
              realizationPhase,                        // прогнозная фаза, на которой риск может наступить
              cause, riskEvent, directConsequence,     // 3 из 5 частей полного описания
              pChecklist: {q1: bool, q2: bool, q3: bool}, p,  // качественная P — детерминированно из чек-листа
              iLevel, iJustification,                  // качественная I — уровень 1-3 + текстовое обоснование
              rra,                                     // P × I, зона L/M/H считается на лету
              quantProbabilityPct, quantScheduleImpactMonths, quantBudgetImpactMln,
              scenarios: {optimistic, mostLikely, pessimistic},  // опционально
              expectedLoss,                            // EL = quantProbabilityPct × quantBudgetImpactMln
              committeeFlag: bool, committeeDecision, committeeDecisionDate,
              residualRra, residualExpectedLoss,
              sourceLessonId (nullable),
              reviewFrequencyDays, nextReviewDate,
              createdAt, closedAt }
Action      { id, riskId, title,
              kind: cause|consequence|contingency|existing_procedure,  // «Вид мероприятия», 4 значения
              strategy: reduce|transfer|avoid|accept,   // стратегия — на уровне мероприятия, не риска
              triggerCondition (nullable),              // текст триггера, только для kind=contingency
              assigneeId, cost,
              plannedDate, forecastActualDate,          // два разных поля даты
              status: planned|in_progress|done|rejected }
Lesson      { id, project, phase, category, title,
              problemOrRiskEvent, description, rootCause,
              impact,                                   // свободный текст, напр. "547 млн ₽ / 10 мес."
              triggerIndicator, strategy,
              lessonLearned, recommendation,
              hashtags: [string],
              sourceRiskId (nullable), createdAt }
RiskDependency { id, fromRiskId, toRiskId, type: усиливает|ведёт_к|зависит_от|дублирует,
                 source: manual|ai_suggested, authorId, createdAt }
AuditLog    { id, riskId, actorId, fromStatus, toStatus, comment, timestamp }
```

## 6. Что осталось на усмотрение при реализации (не блокирует старт разработки)
- Точный текст email/уведомлений комитету при эскалации
- Права на редактирование справочника категорий (сейчас фиксированный список из 8 категорий)
- Формат экспорта отчётов из Privacy Reports & Analytics (PDF/Excel)

**[РЕШЕНО]** Стадия «Закрыт» остаётся пятой стадией конвейера. В изученных реальных данных она не встретилась ни разу (все 15 рисков — в статусе «Мониторинг и Контроль»), но это объясняется тем, что это срез одного текущего проекта, а не отсутствием стадии в принципе: формирование урока (Этап 9) по определению требует триггера «риск закрыт» — без терминального статуса эта ключевая функция приложения не имеет точки запуска. Статус-конвейер остаётся: `Идентификация → Анализ и оценка → Управление → Мониторинг и Контроль → Закрыт`.
